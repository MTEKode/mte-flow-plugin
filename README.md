# mte-flow-plugin

MTE Flow for stock Orca: `mte` Node package, the Claude adapter, and the `mtekode.mte-flow` Orca plugin.

## mte package

`packages/mte` is the `@mtekode/mte` engine (bin `mte`): ESM, Node >= 24, zero runtime dependencies. Sources are TypeScript run directly via Node type stripping (`npm test` runs them as is); `npm pack` (via `prepack`) emits plain JS into `dist/` with `scripts/build.mjs`, because Node refuses to strip types under `node_modules`. Not published to the npm registry; install the tarball attached to the GitHub release:

```sh
npm i -g https://github.com/MTEKode/mte-flow-plugin/releases/download/mte-v0.8.16/mtekode-mte-0.8.16.tgz
```

Development alternative: clone this repo, then `cd packages/mte && npm run build && npm link` (or run `node packages/mte/src/cli.ts <cmd>` straight from the sources).

| Command | What it does |
| --- | --- |
| `mte memory [--role orchestrator] [--workspace <path>]` | Stdio MCP server over one SQLite DB per repo, `<git-common-dir>/mte/memory.db` (shared by all worktrees; `<cwd>/.mte/memory.db` outside git; a legacy `<worktree>/.mte/memory.db` is imported once, never deleted). Orchestrator-only: tools/call is refused for any identity other than the claimed planner (`memory is planner-only`; an unclaimed workspace fails open, and the removed `--role coder|validator` exits with a usage error). Task memory: `record_task` (upsert one row per task), `search_tasks` (FTS5 + `run_id`/`file`/`since`/`until` filters), `get_task`; `search_memory` also returns tasks. |
| `mte check [--json]` | Detects and runs lint/typecheck/test groups; the exit code is the number of failing groups. |
| `mte deploy-check config [--json]` | Prints `<workspace>/.mte/deploy-check.json` (`url`, `username`, `linearDoneState`) plus `hasPassword`; the password is read only from `MTE_DEPLOY_CHECK_PASSWORD` and never printed. |
| `mte deploy-check validated --summary <text> [--failed]` | Comments on the linked Linear issue via `orca linear comment add --current` and, unless `--failed`, runs `orca linear status set --current --to <linearDoneState>`. Exits non-zero when no issue is linked. |
| `mte --version`, `mte help` | |

Tests: `cd packages/mte && npm test` (or `node --test 'packages/mte/**/*.test.ts'` from the repo root). `src/cli.ts` holds the command table that further commands extend.

## Agent setup

`mte install [--workspace <path>]` wires a workspace for Claude in one idempotent step (re-running changes nothing; JSON files are merged, unrelated keys survive; invalid JSON aborts without writing):

| Writes | |
| --- | --- |
| skill | `.claude/skills/mte-flow/{SKILL.md,playbook.md}` |
| hook | `.claude/settings.json` (PreToolUse `Bash` hook `mte guard --claude-hook`) |
| MCP | `.mcp.json` (`mte-memory` = the running node + the absolute CLI entry + `memory`, so it starts without `mte` on PATH; installs that still carry `--role orchestrator` keep working) |
| ignore | `.gitignore` gets `.mte/memory.db*` (covers the SQLite `-wal`/`-shm` files), `.mte/planner.json` (legacy / non-git fallback only), `.mte/guard.log` |

`mte install --user` installs only the `mte-flow` skill (SKILL.md + playbook.md) at user level, with no repo needed: `~/.claude/skills/mte-flow` (Orca's native-chat `CLAUDE_CONFIG_DIR` profile home symlinks `skills` to `~/.claude/skills`, so native chat and terminal both see it). Idempotent; a directory whose `SKILL.md` lacks the `generated by mte install` marker is left untouched, and other skills (such as Orca's bundled `mte`) are never touched. The skill's first step runs `mte install` in the current repo.

`mte` must be on `PATH` (hook, plugin and MCP all call it by name). The supported planner and worker harnesses are `claude` (Claude Code) and `antigravity` (the `agy` CLI). Start a run with `/mte-flow <goal>`. The skill is named `mte-flow` so it cannot be shadowed by Orca's bundled `mte` skill. `mte install` never writes `.agents` (opencode support is retired): it removes previously generated `.agents/skills/{mte,mte-flow}` copies — and the project-level `<dir>/mte` legacy skill — file by file only when their `SKILL.md` carries the `generated by mte install` marker or matches the known generated bytes; a foreign `SKILL.md` leaves the directory untouched.

- **Planner gate**: `mte guard` denies `orca orchestration run-create` and `worker-start` unless the caller is the claimed planner (claim stored per worktree in `<git-dir>/mte/planner.json`, never committed, so parallel runs in sibling worktrees each have their own planner while workers, which run in the Run home worktree, still meet it; an old `<workspace>/.mte/planner.json` is migrated on first read; first claim wins, `mte planner claim --force` replaces). On an unclaimed workspace the hook (`mte guard --claude-hook`, the real interception path) auto-claims the first identified `run-create` caller; a plain `mte guard --command` probe is read-only and never writes the claim. Once a planner is claimed, a caller that presents NO identity is denied too, `mte dispatch` included (fail-open remains only for internal errors); `mte planner release` removes a stale claim so the next claim needs no `--force`. Identity: native chat `ORCA_AGENT_SESSION_ID`, terminal `ORCA_TERMINAL_HANDLE`; a caller matching ANY identity stored in the claim is the planner. `mte planner claim` stores every identity present, taken from env `ORCA_AGENT_SESSION_ID`/`ORCA_TERMINAL_HANDLE`; `--session-id`/`--terminal-handle` are accepted only when the env lacks that identity and are refused when they differ from it (no spoofing). The guard applies the same rule: a contradicting flag denies the command (exit 2, or a hook deny JSON) instead of silently overriding the env.
- **Recognised calls**: `orchestration run-create|worker-start` behind `orca`, any path ending in `/orca`, `"$ORCA_CLI_COMMAND"`/`${ORCA_CLI_COMMAND}`, wrappers `env`/`command`/`exec`/`nohup`/`time`/`sudo`/`xargs`/`nice`, and inside `&&`, `;`, `|`, subshells, real `$(...)`/backtick substitution and the script argument of `bash|sh|zsh|dash -c` / `eval`. Quoted prose, heredoc bodies and backticks inside quotes are data and never parsed as commands. The corrected command is built only from that invocation's own argv (redirections such as `2>&1` and anything after a shell operator are dropped); internal calls (`mte dispatch`) use `$ORCA_CLI_COMMAND` when set, else `orca`.
- **Known limits** (pinned by `shell-parse.test.ts`, not bugs to fix): arbitrary `$VAR` command names are never expanded (only `$ORCA_CLI_COMMAND` resolves), and a substitution glued to a binary name (`orca$(true) orchestration ...`) hides the call. Both simply miss the gate; closing them would mean writing a real shell interpreter, which a cooperative guardrail does not need.
- **Worker pins**: `.mte/worker-pin.json` for coders (`mte pin set --agent <a> --model <m> [--effort <e>]`, `mte pin get --json`) and `.mte/worker-pin-qa.json` for validator and QA workers (same commands with `--role qa`). A `worker-start` carrying neither pin's `--agent/--model/--effort` is denied with the corrected (coder) command. `mte dispatch --task <id> [--role qa] [-- <extra args>]` applies the role's pin itself (`qa` falls back to the coder pin when unset; extra flags win, used for escalation) and exits with orca's code.
- **Fail open**: internal guard errors allow the command and log to `.mte/guard.log`.
- **Not a security boundary**: a cooperative-agent guardrail only. Also set Orca's *Settings > Orchestration > Nested worker depth* to `1` (user setting `nestedWorkerMaxDepth`, not written by `mte`) so dispatched workers cannot start workers.

## Orca plugin

The repo root is the `mtekode.mte-flow` Orca plugin (`orca-plugin.json`, id `mte-flow`, trusted-worker, no build step); the `mte` CLI lives in `packages/mte`. The plugin only drives the `mte` CLI and stock Orca APIs.

Install: in Orca, *Settings > Plugins > Install from Git URL* with `https://github.com/MTEKode/mte-flow-plugin` (or `orca plugin install https://github.com/MTEKode/mte-flow-plugin`).

- **Self-setup**: on activation the worker runs `mte --version`; when `mte` is missing or older than `REQUIRED_MTE_VERSION` it never installs silently (`npm i -g` changes the machine globally): the panel asks for consent and only **Run setup** / **Repair setup** proceed. Then it checks `node` >= 24 and `npm` on PATH (otherwise the panel shows exact instructions and nothing is executed), runs `npm i -g <release tarball>` (never sudo; npm's error text is shown, e.g. for a global prefix you cannot write), then `mte install --user`. When `mte --version` still answers an older version after the install, an older copy is earlier on PATH: Repair updates it (an `mte` owned by another npm prefix is reinstalled there with `npm i -g --prefix`; an old MTE shim is renamed to `<file>.old`; a file that is not recognisably MTE is never touched and the error names it). **Install MTE in this workspace** runs the same repair first when `mte` is older than required. Completion is stored in plugin storage keyed by mte version, so it runs once per version; the **Repair setup** button forces it. The panel's mte row shows the detected `mte` version, and when it sits below `REQUIRED_MTE_VERSION` (possible with manual installs) a drift hint points at Repair setup. Progress shows in the panel and status bar. Plugins cannot read Orca settings, so the panel carries a dismissible reminder to set *Settings > Orchestration > Nested worker depth* = 1.
- **Panel "MTE Flow" (v2, `ui: "html"`, `panel/`)**: an isolated HTML frame themed only with Orca's `--orca-*` variables (colors, `--orca-font-sans`/`--orca-font-mono`, `--orca-radius`), talking to the worker through `orca.plugin.request`. The goal is a plain text box (no search), optional once links are added: an empty goal becomes `Work on the linked item(s): <links>` and a new workspace is named after the links (`eng-1091`). Links field under it: type an identifier or URL (`#45`, `ENG-123`, a GitHub PR/issue URL, a Linear URL, any other http(s) URL) and it shows as the top row of the list (highlighted, so Enter or a click adds it as a chip; a key or number is also looked up, and the matching result with its title takes that row); free text searches instead (Linear via `orca linear search`, GitHub PRs/issues via `gh search` scoped to the workspace's GitHub remote; 300 ms debounce, stale answers dropped) and a suggestion is added only when clicked or chosen with ↑ ↓ then Enter. While it searches, the list shows a spinner row and the field a sweep; each suggestion and chip carries its origin's icon (Linear, GitHub, GitLab, Jira, or a link), PRs and issues are tagged, suggestions already linked show `✓ linked`, and search hints (Linear not connected, no GitHub remote) or `No issues or PRs match.` show in the list. Chips are the run's own links — only what the person added, × removes one at once — and Start run attaches them to the run's workspace (`orca worktree set` / `orca reference add`; failures are named in the start note). The orchestrator selector sits in the form; the coder and QA workers (always terminal) get theirs in a closed **Advanced** section. Each selector has a harness (native, with its icon from `panel/icons`, a letter badge for unknown ones), model (a searchable list grouped by origin, the `provider/` prefix of the id, each group titled with its provider icon; typing an unlisted id offers it as a row) and effort (native); the orchestrator also picks Chat|Terminal. Harnesses come from `orca agent installed`, limited to `claude` and `antigravity`; models are a seed list for claude and a CLI probe for antigravity (`agy models`, cached in plugin storage), plus any ids the person lists per harness in `~/.mte/models.json` (`{ "claude": ["gateway/model"] }`, for models a custom launch command routes to another provider); effort is offered only together with a model. Start run drops a planner claim on its own when `orca agent show` reports the claiming session closed, and launches the planner with `--focus`. A **New workspace** toggle next to Start run creates the run in a fresh Orca worktree instead, and needs no focused workspace: it reveals a repo picker (git repos on every host Orca reaches — this machine, its SSH targets and each paired Orca server, from `orca project setups [--environment <id>]` — shown like Orca's sidebar: a searchable list grouped by host, each repo with its project icon (fetched by the worker as a data URL; otherwise its first letter on the project's badge color) and path, each host with its OS icon (macOS, Windows, Linux) and a server icon when it is not this machine; defaulting to the focused workspace's repo), a name input (empty: a slug from the goal, where a Linear or GitHub URL becomes its key, e.g. `eng-1091`) and a base-branch input (empty: the repo's default base), and `orca worktree create --no-parent` takes the run's links with it (slot links as flags at creation; reference links attach right after, since create cannot mix `--reference` with them), then installs MTE, pins the coder and QA choices and launches the planner in the new workspace. Plus Install MTE, Repair setup, Replace planner, depth reminder and the running orchestrators: one foldable entry per run that has active workers (and per planner started from the panel that has none yet), listing only workers still running (finished, exited and dead ones are dropped) with Focus. Orca records neither who coordinates a run nor the model of a worker, so Start run stores what it launched (planner, coder and QA harness, model, effort) in plugin storage under the planner's session id; a run is tied to that record through the planner claim of the repo its workers run in, and runs started outside the panel show without harness or model. The same setup goes into the bootstrap prompt as a one-line note the planner repeats in its first reply. Worker handlers: `state.get`, `harness.list`, `models.list`, `goal.search`, `run.start`, `workspace.install`, `workspace.focus`, `setup.repair`, `setup.dismiss`, `reminder.dismiss`.
- **Control plane** (0.8.4): each run shows its current phase (`Fase 5/8 · Coder`), read with `mte phase show` from the planner's worktree; the phase is written by the Claude Stop hook `mte phase --claude-hook` (installed by `mte install`), which takes the claimed planner's latest `## Fase N` header from its transcript, so it never depends on the model saving anything. Coders run in child worktrees, so a run is tied to its planner through the worker worktree's `parentWorktreeId`. A **Needs you** list above the runs gathers worker questions and escalations the planner has not handled, pending decision gates (Focus opens the planner's workspace), and settled workers whose terminal Orca still keeps (**Release** runs `orca orchestration worker-release`). Handler: `worker.release`.
- **Remote hosts** (0.8.10): a New workspace on an SSH target or a paired Orca server is created there (`orca worktree create --project-host-setup <id> [--environment <id>]`). The plugin cannot run `mte` on that machine, so an Orca terminal opened in the new workspace runs one line there: `npm i -g <release tarball> && mte install && mte install --user && mte pin set …`. The worker waits for its marker, closes the terminal on success and leaves it open on failure. Then the planner launches there (`--environment` on every call). Agent, model and effort ids must be plain words to cross that shell. The orchestrator list includes workers on paired servers (`worker-list --include-remote`). The remote shell must understand `&&` (sh, bash, zsh, cmd, PowerShell 7; Windows PowerShell 5.1 does not).
- **Agents and models from where the run happens**: harnesses come from `orca agent installed` on the run's machine: the picked repo's host for a New workspace, else the focused workspace's host (`--environment` for a paired server, `--worktree` for an SSH host). The Orchestrator label then reads `Agents and models from <host>`, and the lists reload when that host changes. On another machine, only the built-in model list shows (its model CLI and `~/.mte/models.json` cannot be read from here), with a hint to type a model id.
- **Focused workspace on a paired server**: a workspace your sidebar shows from a paired Orca server is not in this machine's `workspace.list`; the worker finds it on that server (`worktree list --environment <id>`, by instance id, then name and branch), and Start run / Install run there: an Orca terminal in that workspace first asks `mte --version` (npm installs the release only when it is missing or older, so a dev `npm link` stays), then wires the repo, the user skill and the pins; the planner launches there with `--environment`.
- **Focused workspace**: Start run and Install act on the workspace Orca reports as focused; when it reports none (clicking into the panel can do that), the worker uses the last one it saw through `workspace.changed`, which also refreshes the panel.
- **Commands**: `MTE: Open panel` and `MTE: Install in workspace`; starting a run lives only in the panel (the `MTE: Start run` command was removed).
- **Status bar**: `MTE <n>` active workers; one 15 s poller in the worker refreshes the bar and reloads the panel on observable changes (the panel never polls on its own); click opens the panel.
- **Settings**: `plannerAgent` (default `claude`), `plannerModel`, `workerAgent` (default `claude`), `workerModel` (default `sonnet`), `workerEffort` (empty; ignored for agents without effort), `plannerSurface` (`chat`|`terminal`, default `chat`), `plannerEffort`, `mteBin`; they only seed the panel, which remembers its last selection in plugin storage (plugins cannot write settings), (default `mte`). Capabilities: `settings:own`, `storage:own`, workspace read/write, agent read/launch.
- **Start run (terminal planner)**: re-reads the focused workspace at press time (refused when it is the home directory or not a git repo), runs `mte planner show --json` first (a live claim stops the run: the panel names the holder and offers a **Replace planner** button), then `mte install`, `mte pin set ...` (coder, plus `--role qa` when a QA model is chosen), attaches the run's links and, only when replacing, `mte planner release` in its path, then launches the planner with the prompt `/mte-flow <goal>` through `orca agent launch --surface <chat|terminal> [--model m [--effort e]] --prompt` (a chat that Orca opens as a terminal instead is reported in the panel) (goal truncated with a marker to stay under the 4000-char cap). The host `agent.launch` is only a fallback when the CLI is missing: it sends the prompt in a second, fire-and-forget call that failed silently in QA.
- **Which Orca**: the worker's env has no `ORCA_*`, so the plugin derives the hosting app's CLI from `process.execPath` (`<app>/Contents/Resources/bin/orca` on macOS, `resources/bin/orca-ide` on Linux, `resources/bin/orca.exe` on Windows) and the profile from its own install path (`<userData>/plugins/<key>/<hash>/`), and runs the CLI with `ORCA_USER_DATA_PATH` set. A dev-linked plugin has no userData in its path and uses the bundle's default profile.
- Requires the `mte` CLI: `npm i -g https://github.com/MTEKode/mte-flow-plugin/releases/download/mte-v0.8.16/mtekode-mte-0.8.16.tgz` (dev alternative: clone this repo, then `cd packages/mte && npm run build && npm link`). The panel shows this when `mte` is missing or `mte --version` exits non-zero.
- `plannerModel` is passed to the planner launch (`--model`); empty means the agent's default. An empty `workerModel` skips `mte pin set`.

Develop and test (from the repo root; none of these install into your Orca profile):

```sh
orca plugin validate .
orca plugin check .
orca plugin test .            # or: node --test "test/**/*.test.mjs"
```

## End-to-end run (opt-in)

`e2e/` drives one full MTE run with real models: a planner (Claude Agent SDK, default `sonnet`) loads the installed `mte-flow` skill, guard hook and memory MCP; a simulated user (default `haiku`) answers its proposals and questions; the workers are real Orca workers pinned to cheap models (`haiku` coders, `sonnet` QA). It checks every phase header in order, that AskUserQuestion is used only in grill-me (brainstorming and the requirements lock are text conversation, answered before moving on), QA after the coder, `record_task`, and the draft PR (a fake `gh` that never reaches GitHub). A hidden acceptance check then runs on the branch the planner pushed.

```sh
cd e2e && npm install && npm run e2e   # needs Orca running, `mte` and a logged-in `claude` on PATH
npm test                               # unit tests of the flow assertions only (free)
```

The fixture lives in `~/orca/mte-e2e-fixture` (override with `MTE_E2E_REPO`), is registered in Orca once and reset on every run. Knobs: `MTE_E2E_PLANNER_MODEL`, `MTE_E2E_USER_MODEL`, `MTE_E2E_WORKER_MODEL`, `MTE_E2E_QA_MODEL`, `MTE_E2E_MAX_TURNS`, `MTE_E2E_TIMEOUT_MIN`, and `MTE_E2E_USER_SETTINGS=1` to also load your `~/.claude` config. Transcript and verdict land in `e2e/out/<timestamp>/`.
